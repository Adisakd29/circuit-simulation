# ประเมินตัวจำลอง ESP32 (แผนข้อ 6 · 2026-10-30)

> **สถานะ (อัปเดต 2026-11-25):** ผู้ใช้เลือกทาง "QEMU บนเซิร์ฟเวอร์" แล้ว · ESP32-DevKitC V4 รองรับแบบ **จำลองบางส่วน** ตั้งแต่รอบ 83 (`docs/REPORT.md` หัวข้อ 83, `server/esp32/README.md`) — รัน **MicroPython** (ไม่ใช่ Arduino C/C++ ที่ประเมินไว้ด้านล่าง เพราะเลี่ยงชุดคอมไพเลอร์ ~1.4 GB ได้) และตัวจำลองวงจรทำงานบนเซิร์ฟเวอร์คู่กับ QEMU ทำให้ lockstep ได้ (ข้อสรุปในหัวข้อ 4 ที่ว่า lockstep กับตัวจำลองในเบราว์เซอร์ทำไม่ได้ยังถูกต้อง) · ใบอนุญาต ROM ยังเป็นความเสี่ยงที่เหลือ (หัวข้อ 5) · เนื้อหาด้านล่างคือผลประเมินเดิม 2026-10-30

**เลือกทดลองตัวเลือก C** เพราะเป็นตัวเดียวที่ส่งเหตุการณ์ขาออกมาให้ตัวจำลองวงจรของเราใช้ได้

## 2. สิ่งที่ทดลองจริง (ยืนยันแล้ว — มีโค้ดและล็อกใน `tools/esp32-proto/`)

ทดลองบนเครื่องทดสอบ (คอนเทนเนอร์ Linux 2 CPU) ด้วย arduino-esp32 core 3.3.12 ผ่าน arduino-cli 1.1.1 บอร์ด `esp32:esp32:esp32:FlashSize=4M,FlashMode=dio`

| รายการ | ผล |
|---|---|
| คอมไพล์ | ครั้งแรก ~20 วินาที ครั้งถัดไป ~13 วินาที ได้ไฟล์ merged.bin ขนาด 4 MB · **โหมด QIO บูตใน QEMU ไม่ได้ ต้องใช้ DIO** |
| บูต | บูตจาก ROM ถึง `setup()` ได้ (ล็อก `ets Jul 29 2019` → `entry 0x4008059c`) · ใช้เวลาจริง ~5.7 วินาทีเมื่อเปิด `-icount` |
| ความแม่นยำของเวลา | เปิด `-icount shift=2` (4 ns ต่อคำสั่ง) แล้ว `delay(100)` ได้คาบ 100.000 ms ทุกครั้ง · เวลาเสมือนกำหนดได้แน่นอน (deterministic) |
| ความเร็ว | โค้ดที่ใช้ CPU ล้วนรันได้ ~0.92 เท่าของเวลาจริง (~230 MIPS) · `shift=3` รันโค้ดที่มี delay มากได้ราว 3 เท่าของเวลาจริง |
| ทรัพยากร | **1 คอร์เต็ม 100% และ RSS ~165–170 MB ต่อบอร์ดที่กำลังรัน** · ถ้าไม่ใช้ icount จะเป็น TCG หลายเธรด ใช้ RSS 585–784 MB และเวลาแกว่ง |
| GPIO ออก | callback `write_pin` ได้ทุกขอบพร้อมเวลาเสมือน (เช่น `pin GPIO21=1 t=780.138148 ms`) |
| GPIO เข้า | เรียก `qemu_picsimlab_set_pin` จาก callback ได้ทันที · ทดสอบวนกลับ GPIO2 → GPIO15 แล้ว `digitalRead(15)` สลับ 0/1 ตรงกับที่ป้อน |
| ADC | `qemu_picsimlab_set_apin(6, 2048)` แล้ว `analogRead(34)` อ่านได้ 2048 |
| UART | callback `uart_tx_event` ได้ทีละไบต์พร้อมเวลาเสมือน |
| I²C | ทำงานระดับธุรกรรม (START/WRITE/READ/STOP) ผ่าน callback `i2c_event` · สแกนบัสเห็นเฉพาะ 0x40 ที่ตอบ ACK · อ่านรีจิสเตอร์ได้ `reg0=0x1234` ตามค่าที่ callback ส่งกลับ · ครั้งแรกที่ลองได้ผลผิดเพราะตีความรหัสเหตุการณ์ผิด รหัสจริงคือ enum `i2c_event` ของ QEMU (0–2 = START, 3 = STOP, 5 = WRITE, 6 = READ) · repeated start (`endTransmission(false)`) ส่งมาเป็น STOP + START |
| PWM (LEDC) | ขาไม่สลับ มีเพียงเหตุการณ์ `GPIO4=0` ครั้งเดียว · อ่านรีจิสเตอร์ผ่าน `get_internals` ได้ duty 25.098% (64/255), timer 1000 Hz และ `gpio_out_sel[4]=71` (สัญญาณ LEDC HS ch0) · **ถ้าจะแสดง PWM ต้องสร้างรูปคลื่นจากรีจิสเตอร์เอง** เหมือนที่ทำกับ Uno |
| INPUT_PULLUP | ขาที่ไม่ได้ต่ออะไรอ่านได้ 0 เพราะไม่ได้จำลอง pull-up · ตัวจำลองวงจรของเราต้องป้อนระดับเองทุกขา |

## 3. ขนาดที่ต้องเพิ่มบนเซิร์ฟเวอร์ (Railway)

| ส่วน | ขนาด |
|---|---|
| arduino-esp32 core | 83 MB |
| esp32-libs | 184 MB |
| ชุดคอมไพเลอร์ esp-x32 | 1.1 GB |
| esptool | 81 MB |
| libqemu-xtensa.so | 59 MB |
| **รวม** | **~1.5 GB เพิ่มใน Docker image** (ถ้าติดตั้งทุกชิปจะได้ 7.8 GB ต้องลบชิปอื่นออก) |

- ติดตั้ง core ครั้งแรกใช้ 2 นาที 54 วินาที · build QEMU ใช้ 4.5 นาที เวลา build image บน Railway จึงนานขึ้นมาก
- **ภาระขณะใช้งาน:** นักเรียน 1 คนที่กด Run ESP32 ใช้ 1 vCPU + ~170 MB ตลอดเวลาที่รัน ถ้ามีนักเรียน 30 คนรันพร้อมกันจะต้องใช้ราว 30 vCPU และ 5 GB RAM ต้องมีคิว/จำกัดเวลา/จำกัดจำนวนพร้อมกัน

## 4. ปัญหาด้านสถาปัตยกรรม

ตัวจำลองวงจรของเราทำงานในเบราว์เซอร์ และตอนนี้ AVR/RP2040 ทำงานแบบ lockstep ทุก 50 µs ส่วน QEMU ต้องรันบนเซิร์ฟเวอร์ (เป็น C + GPL) **การทำ lockstep 50 µs ข้ามเครือข่ายจึงเป็นไปไม่ได้** ทางเลือกมีดังนี้

1. **ย้ายตัวจำลองวงจรไปฝั่งเซิร์ฟเวอร์สำหรับโปรเจกต์ ESP32** — engine ของเราเป็น TypeScript ที่รันบน Node ได้อยู่แล้ว (ชุดทดสอบ unit รันบน Node ทั้งหมด) เซิร์ฟเวอร์จะรัน QEMU + engine คู่กันในกระบวนการแยก แล้วส่งสถานะขา/ค่าวัดไปให้เบราว์เซอร์วาดเท่านั้น I²C callback แบบ synchronous ก็ตอบจากโมเดลอุปกรณ์ตัวเดียวกันได้ · ได้ความแม่นยำเท่ากับบอร์ดอื่น แต่ใช้ 1 vCPU ต่อนักเรียน และหน่วงตามเครือข่ายเฉพาะตอนแสดงผล/ปุ่มกด
2. **เชื่อมแบบหลวม** — QEMU ส่งเหตุการณ์ขาไปเบราว์เซอร์ และเบราว์เซอร์ส่งค่าอินพุตกลับ ค่าอินพุตจะช้าตามเครือข่าย (หลายสิบถึงหลายร้อย ms) · I²C/SPI ทำไม่ได้ เพราะ callback ต้องได้คำตอบทันที · **ไม่แม่นยำ ต้องบอกผู้ใช้ และไม่ควรใช้กับงานที่ขึ้นกับเวลา**
3. **ตัวจำลองในเบราว์เซอร์** (เช่น ESP32-C3 แบบ RISC-V เขียนด้วย JS/WASM) — ไม่มีภาระเซิร์ฟเวอร์และทำ lockstep ได้ แต่ต้องเขียนตัวจำลอง CPU และอุปกรณ์รอบข้างเอง ซึ่งเป็นงานใหญ่มาก · คอมไพล์ยังต้องทำบนเซิร์ฟเวอร์ (~1.5 GB เหมือนเดิม) · Velxio ประกาศว่ากำลังทำแนวนี้ แต่โค้ดเป็น AGPL

## 6. สิ่งที่ยังไม่ได้ทดสอบ

- Wi-Fi (fork มี `esp32_wifi*.c` แต่ยังไม่ได้ลอง) · Bluetooth (ไม่มีทั้งสามตัวเลือก)
- SPI callback, RMT (NeoPixel), touch, DAC, deep sleep, ESP32-S3/C3
- จำนวนบอร์ดที่รันพร้อมกันได้จริงบนแผนของ Railway (ยังไม่ได้ deploy · ตัวเลขข้อ 3 วัดจากคอนเทนเนอร์ทดสอบ)
- ความต่างจากบอร์ดจริง (ยังไม่มีบอร์ดจริงให้เทียบ)

## 7. ข้อเสนอ

- **ไม่แนะนำตัวเลือก 4.2 (เชื่อมแบบหลวม)** เพราะขัดกับหลัก "ห้ามจำลองหลอก" ในเรื่องเวลาและ I²C
- **ถ้างบเซิร์ฟเวอร์รองรับ ~1 vCPU ต่อนักเรียนที่รัน ESP32 พร้อมกันได้** ให้ทำตัวเลือก 4.1 เป็นขั้น ๆ: (1) อิมเมจคอมไพล์ ESP32 แยกบริการ (2) QEMU + engine ในกระบวนการแยกต่อเซสชัน มีคิวและจำกัดเวลา 5 นาที (3) GPIO/ADC/UART/I²C/LEDC ก่อน แล้วแสดงสถานะ Partial ตามจริง
- **ถ้างบไม่พอ** ให้เลื่อน ESP32 ออกไป แล้วทำข้อ 1–5 ที่เหลือให้ครบก่อน · หรือรอตัวจำลองในเบราว์เซอร์ที่ใบอนุญาตใช้ได้
- ต้องแก้เรื่องใบอนุญาต ROM ก่อนทั้งสองทาง
